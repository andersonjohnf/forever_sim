# What's New and Release history (2026-09-24)

The release notes (`5bced2b8`) and What's New with Release history (`44a57981`) had a combined logic
and UX review by a fresh reviewer who wrote neither. This log records its findings and the fix round
that answered them. The fixes changed what What's New shows and when the load's notices appear, so
they get a verification pass by a fresh reviewer (D25).

Probes: the reviewer's `.cache/probes/wn-review/` (`probe.mjs`, `probe2.mjs`, `probe3.mjs`) in its
worktree; the fix round's `.cache/probes/wn-fix/probe.mjs` in its own (What's New with a pasted
link's toast, the held notice after closing, All releases, at 1280 × 900, 1280 × 720 and 390 × 844,
light and dark).

## Findings

| # | Severity | Origin | Finding | Disposition |

| WN-1 | medium | introduced | The push that ships What's New needs its own release entry at the top of `src/app/releases.ts`, or the rollout says nothing about itself. | The lead adds the entry with the push, since it has to cover everything merged since the last deploy. The code and tests are ready for a new top entry: nothing names a release id, and `releases.test.ts` checks that a new top entry shows alone to a visitor on today's newest and to one from before What's New (`10f5c275`). |
| WN-2 | medium | introduced | The first-visit rule hid the rollout from every existing player: no one has a stored id yet, so everyone counted as a first visit and saw nothing. | Fixed in `10f5c275` and `048bec72`. With no id but an automatic save (`forever-sim:setup`) or named setups (`forever-sim:saved-setups`), the visitor counts as having seen the release before the newest and sees the newest alone. `checkReleases` still runs in What's New's first render (its `useState` initializer), before `useSharedLink`'s effect can write the automatic save. A comment in `whats-new.tsx` and the architecture doc say so, and an e2e test shows a first visit from a share link is still a first visit. Unit and e2e tests cover both keys; ux.md "What's new" and architecture.md "Release notes" follow. |
| WN-3 | low | introduced | An id the list didn't know was always overwritten with the newest, including one from a newer release (a tab that saw it, then a rollback). Going forward again would show that release twice. | Fixed in `10f5c275`: an unknown id is replaced only if it sorts older (`compareReleaseIds`: the date, then the day's number as a number, so `.10` comes after `.9`) or isn't a release id; a newer one is kept. Unit tests cover older, junk and newer ids, plus an e2e test for a newer id. |
| WN-4 | low | introduced | At 1280 px, the shared link's toast covered the left of Got it. | Fixed in `048bec72`: while a toast is up, the footer's bottom padding grows by `--toast-clearance` (dialog and phone sheet). Since WN-5, only a link pasted in while What's New is open can raise one. An e2e test (desktop and phone) checks the left, middle and right of Got it and All releases once the toast has settled, and fails without the padding. |
| WN-5 | low | introduced | The load's toasts (the link's notice, the defaults notice) competed with the dialog, timed out while it was open, and weren't heard, since the dialog hides the page from screen readers. | Fixed in `048bec72`: they wait (`src/app/held-toasts.ts`) and come up once What's New has closed and unmounted, or once Release history closes after All releases. e2e tests check that nothing shows while it's open, the notice shows after it closes, and no ancestor of the toaster is `aria-hidden` or `inert`. A link pasted in later is not held. |

New e2e tests cover What's New with the defaults notice and WN-2's rule (`048bec72`). |
